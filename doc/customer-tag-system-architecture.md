# 音乐 App 客户标签管理系统 — 业务架构与技术架构

| 项目 | 内容 |
|---|---|
| 文档版本 | V1.0 |
| 状态 | 架构基线（待研发、运营、合规评审） |
| 适用范围 | SonicHub 音乐 App 的 C 端用户标签、B 端租户标签、运营人群圈选 |
| 承载系统 | 现有 `SonicHub_api`（Go + go-zero + PostgreSQL）、`SonicHub_admin`（Vue 管理端） |
| 关联文档 | `docs/requirements.html`、用户与积分架构设计 |

---

## 0. 决策摘要

**决策问题**：如何在现有 Go 模块化单体中，建设一套口径可治理、结果可追溯、可用于运营触达的客户标签体系，同时不破坏已有的权限、积分、作品与合规边界？

**核心决策**：

1. 标签系统作为 `SonicHub_api` 内的独立模块（`internal/tag`）落地，不新建独立标签平台服务。
2. PostgreSQL 保存标签定义、规则版本、标签结果、变更历史与人群包快照；Redis 只做位图索引与画像缓存，不做事实源。
3. 标签是"画像事实"，**不是权限事实、也不是积分事实**。标签不得直接授予权益或修改余额，只能作为运营决策输入。
4. 标签分为事实、统计、规则、模型、人工五类，统一走"定义 → 版本 → 试算 → 审批 → 生效 → 下线"的治理流程。
5. 标签主体支持 `user`（C 端用户）、`tenant`（企业租户）、`member`（租户内成员）三种，避免"一人多租户"场景下画像串味。

**需要付出的代价**：需要维护标签口径版本、计算任务调度、位图重建和敏感标签审批，运营侧新增一套治理流程；短期交付速度慢于"直接在后台加一列 tag"。

**什么时候要重新决策**：单日标签计算超过 4 小时、位图内存超过 Redis 实例容量 30%、或需要跨部门共享标签资产时，再评估拆分独立标签服务与引入列式分析库。

## 1. 业务架构

### 1.1 业务目标与约束

| 维度 | 内容 |
|---|---|
| 业务目标 | 让运营能够按"客户是谁、做过什么、可能想要什么"分层触达，而不是全量群发 |
| 成功标准 | 新用户 7 日首作率提升、额度耗尽前付费转化率提升、沉默用户召回率提升、企业租户流失提前预警 |
| 硬约束 | 标签口径必须可解释、可回溯；敏感标签访问必须留痕；标签不得覆盖用户权限与积分事实 |
| 非目标 | 不做实时个性化推荐排序引擎（仍由 feed 模块负责）、不做广告投放平台、不做用户级定价歧视 |
| 已知限制 | 现有 `feed_impressions`、`share_events` 等行为数据存在，但没有统一客户画像层；标签口径分散在运营表格中 |

### 1.2 "客户"的定义与标签主体

音乐 App 的"客户"不是单一实体，必须区分三种主体，否则"企业管理员"和"个人创作者"会被混成一个画像。

| 主体类型 | 对应现有表 | 典型标签 | 用途 |
|---|---|---|---|
| `user` | `users` | 生命周期阶段、创作风格偏好、付费意愿、流失风险 | C 端运营、推荐冷启动 |
| `tenant` | `tenants` | 租户健康度、席位使用率、商用授权状态、续费风险 | B 端客户成功、销售跟进 |
| `member` | `memberships` | 租户内角色、活跃度、是否为关键决策人 | 企业内推广、权限治理 |

**关键规则**：同一个自然人在个人租户和企业租户下的行为必须分别归属。生成任务、积分消耗按 `tenant_id` 归属；登录、设备、内容消费按 `user_id` 归属。跨主体聚合只允许在"客户 360 视图"中展示，不允许写回单一标签。

### 1.3 标签分层模型

| 层级 | 来源 | 示例标签编码 | 更新频率 | 可信度 |
|---|---|---|---|---|
| 事实标签（fact） | 注册资料、订单、租户状态 | `user.profile.registered_channel`、`tenant.billing.plan_type` | 实时/事件驱动 | 高，可直接对账 |
| 统计标签（metric） | 行为与交易聚合 | `user.usage.gen_count_30d`、`user.billing.credit_spend_30d` | 小时/T+1 | 高，可复算 |
| 规则标签（rule） | 多条件组合判定 | `user.lifecycle.stage`、`user.creation.style_pref` | 小时/T+1 | 中高，依赖口径 |
| 模型标签（model） | 预测模型输出 | `user.billing.upgrade_propensity`、`tenant.health.churn_risk` | T+1/周 | 中，必须带置信度 |
| 人工标签（manual） | 运营/客服/客户成功手工标注 | `user.service.vip_flag`、`tenant.success.key_account` | 随时 | 人工权威，需过期时间 |

**命名规范**：`{主体}.{域}.{属性}`，全小写点号分隔，域限定在 `profile / usage / creation / billing / lifecycle / service / risk / health`。编码一经发布不可改名，只能新增版本或标记废弃。

**覆盖优先级**：`manual > model（置信度 ≥ 阈值） > rule > fact`。同层冲突时以 `updated_at` 较新者为准，并把冲突写入变更历史，禁止静默覆盖人工标签。

### 1.4 标签资产治理

| 环节 | 规则 | 责任角色 |
|---|---|---|
| 新建 | 必须填写编码、主体、业务口径、数据来源、更新频率、是否敏感、预期用途 | 标签 Owner（运营） |
| 口径变更 | 生成新版本，旧版本保留；生效中任务使用旧版本直至结束 | 标签 Owner + 数据研发 |
| 试算 | 上线前必须试算命中人数与抽样样本，偏差超阈值需说明 | 数据研发 |
| 审批 | 敏感标签、跨租户使用、批量导出需审批 | 数据合规 + 业务负责人 |
| 监控 | 命中率突变、空标签率、口径漂移告警 | 数据研发 |
| 下线 | 先置 `deprecated` 停止写入，观察 30 天后置 `archived`，保留历史供审计 | 标签 Owner |

**下线规则**：任何人不得物理删除标签定义与历史结果；`archived` 仅停止计算和查询，历史数据按保留策略归档。

### 1.5 六类业务场景

#### 场景 S1：新用户冷启动引导

| 项目 | 内容 |
|---|---|
| 业务问题 | 新用户注册后不知道输入什么 Prompt，7 日内不产出首作即流失 |
| 触发条件 | 注册后 24 小时且 `user.usage.gen_count_7d = 0` |
| 依赖标签 | `user.lifecycle.stage = new`、`user.profile.registered_channel`、`user.creation.onboarding_completed` |
| 业务动作 | 首页下发 3 个场景模板（短视频 BGM / 广告配乐 / 铃声），推送一次引导消息 |
| 成功指标 | 7 日首作率、模板点击率、首作完成时长中位数 |
| 失败与边界 | 用户已关闭推送则不触达，只做站内展示；同一用户 7 日内最多触达 2 次 |

#### 场景 S2：创作偏好标签驱动推荐

| 项目 | 内容 |
|---|---|
| 业务问题 | 首页推荐与生成默认参数不区分用户风格偏好，导致反复试错 |
| 触发条件 | 用户完成 ≥ 3 次生成，或收藏/点赞 ≥ 5 个作品 |
| 依赖标签 | `user.creation.style_pref`（枚举：国风/电子/流行/影视配乐…）、`user.creation.duration_pref`、`user.creation.vocal_pref`、`user.creation.multitrack_pref` |
| 业务动作 | 生成工作台预填风格与时长；首页提高偏好风格作品权重 |
| 成功指标 | 生成参数修改率下降、二次生成率、作品收藏率 |
| 失败与边界 | 偏好标签置信度 < 0.6 时不下发预填，避免误导；标签 30 天未更新按时间衰减重算 |

#### 场景 S3：额度耗尽前的付费转化

| 项目 | 内容 |
|---|---|
| 业务问题 | 用户积分用完才看到付费页，转化路径被动 |
| 触发条件 | 可用积分 < 单次生成均价 × 2，且 30 日内生成 ≥ 3 次 |
| 依赖标签 | `user.billing.credit_exhaust_risk`（high/medium/low）、`user.billing.paid_before`、`user.billing.arpu_band` |
| 业务动作 | 生成页展示"即将不足"提示与首充礼包；对 `paid_before = true` 用户展示续费套餐 |
| 成功指标 | 充值转化率、礼包点击率、客单价 |
| 失败与边界 | 标签只决定展示策略，**不得对不同用户展示不同价格**；未成年人标签用户不参与付费营销 |
| 数据一致性 | 积分余额以 `credit_accounts` 为准，标签只做区间判断，不做余额缓存 |

#### 场景 S4：沉默用户召回

| 项目 | 内容 |
|---|---|
| 业务问题 | 沉默用户召回依赖全量短信，成本高且打扰大 |
| 触发条件 | 连续 30 天未登录，且历史有 ≥ 1 个作品 |
| 依赖标签 | `user.lifecycle.stage = dormant`、`user.creation.last_work_age`、`user.service.recall_sensitivity`（高/中/低） |
| 业务动作 | 按敏感度分层：高敏感只做站内信，中低敏感叠加短信；附"未完成作品继续创作"入口 |
| 成功指标 | 召回率、7 日回访后二次创作率、退订率 |
| 失败与边界 | 30 日内已触达 2 次则跳过；用户注销/冻结状态直接排除；退订用户永久排除 |

#### 场景 S5：创作者分层与激励

| 项目 | 内容 |
|---|---|
| 业务问题 | 平台无法识别高潜力创作者，激励资源平均分配 |
| 触发条件 | 作品 ≥ 5 个且近 30 日互动量进入前 10% |
| 依赖标签 | `user.creation.creator_tier`（普通/潜力/优质/头部）、`user.creation.engagement_score`、`user.risk.content_violation_flag` |
| 业务动作 | 分级给予曝光位、免费额度、官方推荐；有违规标记的创作者不进入激励池 |
| 成功指标 | 优质创作者留存、作品产出量、被推荐作品完播率 |
| 失败与边界 | `content_violation_flag` 来自 `moderation_cases`，标签只读不写；申诉成功需在 24 小时内同步标签 |

#### 场景 S6：企业租户客户成功

| 项目 | 内容 |
|---|---|
| 业务问题 | B 端续费依赖人工盘点，发现流失信号太晚 |
| 触发条件 | 席位激活率 < 50%，或近 30 日生成量环比下降 ≥ 40% |
| 依赖标签 | `tenant.health.seat_activation`、`tenant.usage.gen_trend_30d`、`tenant.billing.renewal_window`、`tenant.success.key_account` |
| 业务动作 | 生成客户健康度看板，按风险排序推送 CSM 待办；高价值租户触发人工回访 |
| 成功指标 | 续费率、席位激活率、风险租户回访覆盖率 |
| 失败与边界 | 标签只对具备 `tenant:tag:read` 权限的 CSM 可见；不得向企业成员暴露租户风险标签 |

#### 场景 S7：风控与合规辅助

| 项目 | 内容 |
|---|---|
| 业务问题 | 批量注册、盗用积分、违规内容重复出现 |
| 触发条件 | 同设备多账号、异常生成频率、多次审核拒绝 |
| 依赖标签 | `user.risk.multi_account_flag`、`user.risk.abnormal_usage`、`user.risk.content_violation_flag` |
| 业务动作 | 进入人工审核队列、限制任务并发、触发二次验证 |
| 成功指标 | 风险账号识别率、误封率、审核队列准确率 |
| 失败与边界 | **风控标签不得自动执行封禁**，必须经人工或既有 `user_dispositions` 流程；标签访问需审批并全部审计 |

### 1.6 业务指标与验收

| 指标 | 定义 | 初始目标 | 数据来源 |
|---|---|---|---|
| 标签覆盖率 | 至少 1 个有效标签的用户 / 活跃用户 | ≥ 80% | `tag_assignments` |
| 标签准确率 | 人工抽检与标签值一致的比例 | ≥ 95%（事实/统计）、≥ 80%（模型） | 抽检记录 |
| 新用户 7 日首作率 | 注册 7 日内完成 ≥1 次生成 | [TBD] 基线 + 相对提升 | `generations` |
| 召回率 | 触达后 7 日内回访比例 | [TBD] 基线 + 相对提升 | 触达与登录日志 |
| 人群圈选时效 | 从提交圈选到可导出 | ≤ 5 分钟（百万级） | `tag_jobs` |
| 标签口径可追溯率 | 扣费/触达可回溯到规则版本 | 100% | `tag_assignment_history` |

## 2. 技术架构

### 2.1 上下文映射

```
                    ┌──────────────────────────────────────────┐
                    │        SonicHub_admin (Vue)              │
                    │  标签管理台 / 客户360 / 人群圈选 / 审批   │
                    └───────────────────┬──────────────────────┘
                                        │ /admin/v1/tags ...
┌───────────────────────────────────────▼──────────────────────────────────────┐
│                          SonicHub_api (Go 模块化单体)                         │
│                                                                              │
│  ┌──────────┐   ┌──────────┐   ┌──────────────┐   ┌────────────────────┐     │
│  │  Identity│   │  Billing │   │  Generation  │   │   Feed / Content   │     │
│  │ users    │   │ credits  │   │  generations │   │  works / comments  │     │
│  └────┬─────┘   └────┬─────┘   └──────┬───────┘   └─────────┬──────────┘     │
│       │ UserContext  │ events          │ events              │ events         │
│       └──────────────┴─────────────────┴─────────────────────┘                │
│                                        ▼                                     │
│                    ┌────────────────────────────────────┐                    │
│                    │        TAG MODULE (new)            │                    │
│                    │  定义/版本 · 规则求值 · 计算任务    │                    │
│                    │  标签结果 · 人群包 · 访问审计        │                    │
│                    └──────────────┬─────────────────────┘                    │
│                                   │ 只读查询                                  │
│                    ┌──────────────▼─────────────────────┐                    │
│                    │ Notification / Messaging / 权益下发 │                    │
│                    └────────────────────────────────────┘                    │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │
        ┌───────────────────────┼────────────────────────┐
        ▼                       ▼                        ▼
  PostgreSQL              Redis (bitmap/cache)     Outbox → Worker
  标签事实与历史           画像查询加速              计算/圈选/触发
```

**上下文关系**：

| 相邻上下文 | 关系 | 翻译面 |
|---|---|---|
| Identity | 上游（customer/supplier） | Tag 只读 `users/tenants/memberships`，不复刻角色与状态 |
| Billing | 上游（customer/supplier） | 只消费 `credit_ledger`、`orders` 聚合，禁止写余额 |
| Generation | 上游（customer/supplier） | 消费 `generations` 状态与参数摘要，不持有 Prompt 全文 |
| Content | 上游 | 消费 `works`、`work_likes`、`comments` 聚合 |
| Notification | 下游（conformist） | 接收 `tag.segment.materialized` 事件，按人群包触达 |
| Admin | 下游（UI） | 只通过 Admin API 访问，不直连数据库 |

### 2.2 模块内部分层

```
internal/tag
├── domain           标签定义、版本、赋值、规则 AST、人群包（纯 Go，无 IO）
├── app              用例：定义标签、发布版本、触发重算、圈选、导出
├── infra
│   ├── repository    PostgreSQL 仓储（pgx），强制 subject_type + 过滤条件
│   ├── bitmap        Redis Roaring Bitmap 索引，可按版本重建
│   └── sources       从 identity/billing/generation/content 只读聚合
└── transport        HTTP handler（admin + internal）、事件消费者
```

**依赖方向**：`transport → app → domain`，`infra` 实现 `domain` 定义的接口。Tag 不得反向依赖其他业务模块的内部仓储，只能依赖其暴露的只读查询接口或事件。

### 2.3 数据模型

| 表 | 关键字段 | 说明 |
|---|---|---|
| `tag_definitions` | `id, code, name, subject_type, category, value_type, description, is_sensitive, source_type, status, owner_user_id` | 标签主数据；`code` 唯一且不可改 |
| `tag_values` | `tag_id, value_code, label, sort_no` | 枚举值字典；数值/布尔型可空 |
| `tag_versions` | `id, tag_id, version, rule_expr, window_spec, schedule, status, effective_from, effective_to, change_reason, approved_by` | 口径版本；同一标签同时只有 1 个 `active` |
| `tag_assignments` | `subject_type, subject_id, tag_id, value, confidence, source, rule_version_id, valid_from, expires_at, updated_at` | 当前结果，主键 `(subject_type, subject_id, tag_id)` |
| `tag_assignment_history` | `id, subject_type, subject_id, tag_id, old_value, new_value, source, rule_version_id, reason, operator_id, event_id, created_at` | 只追加，用于追溯与对账 |
| `tag_jobs` | `id, tag_id, version_id, mode(full/incremental), window_start, window_end, status, processed, matched, failed, error, started_at, finished_at` | 计算任务，`(tag_id, version_id, window_end, mode)` 唯一 |
| `tag_job_checkpoints` | `job_id, shard_no, cursor` | 分片断点，支持断点续算 |
| `segment_definitions` | `id, name, subject_type, expr, status, created_by, last_computed_at` | 人群包定义（标签表达式） |
| `segment_snapshots` | `id, segment_id, computed_at, member_count, bitmap_uri, expires_at` | 人群快照；`bitmap_uri` 指向对象存储 |
| `segment_members` | `segment_id, snapshot_id, subject_id` | 小额人群包物化（≤ 10 万）用于导出 |
| `tag_field_registry` | `id, subject_type, field_code, data_type, source_module, aggregation, is_sensitive, status` | 规则可引用字段登记表；未登记字段禁止发布 |
| `tag_import_batches` | `id, tag_id, file_uri, total, succeeded, failed, status, operator_id, approved_by` | 人工导入批次 |
| `tag_access_audits` | `id, actor_id, action, subject_type, tag_id, segment_id, filter_summary, row_count, ip, created_at` | 敏感标签查询/导出审计 |

**约束**：

- `tag_assignments` 对 `is_sensitive = true` 的标签不做明文扩展，敏感值走独立加密列或令牌化映射。
- 账户、余额、权限相关字段不得复制进标签表；标签只存区间或枚举。
- 所有表带 `created_at`，历史表只允许 `INSERT`。

### 2.4 标签计算链路

```
行为/交易事件（outbox 已存在）
        │
        ├─ 实时层：事件 → 单主体增量聚合 → 直接更新高时效标签（≤5 分钟）
        │
        └─ 批量层：定时任务 → 按窗口扫描事实表 → 规则求值 → 标签写入 + 历史 + 事件
                                        │
                                        ▼
                              Redis Bitmap 增量更新
                                        │
                                        ▼
                          人群包圈选 → 快照 → 通知/导出
```

| 时效等级 | 适用标签 | 机制 | 目标延迟 |
|---|---|---|---|
| 实时 | 注册渠道、当前套餐、最近一次生成时间 | 事件驱动 | ≤ 5 分钟 |
| 小时 | 30 日生成次数、积分消耗、活跃度 | 定时增量任务 | ≤ 1 小时 |
| T+1 | 生命周期阶段、创作者分层、流失风险 | 全量批算 | 每日 06:00 前完成 |
| 周 | 模型标签（付费倾向、租户健康度） | 离线训练 + 批量写入 | 每周一次 |

**计算任务幂等**：以 `(tag_id, version_id, window_end, mode)` 唯一键抢占任务；每个分片独立事务提交标签与历史；重复执行结果一致，不产生重复历史（历史按 `event_id` 去重）。

**大数据量处理**：按 `subject_id` 哈希分片（默认 16 片），每片 5 万条一批，通过 `tag_job_checkpoints` 断点续算，避免长事务与锁表。

### 2.5 规则表达式设计

不使用任意脚本执行，提供受限 DSL，仅允许白名单函数与已登记字段。

```
subject = user
window  = 30d
when all(
  count(generation.completed, 30d) >= 5,
  sum(credit.captured, 30d) >= 300,
  last(work.published_at) within 14d
)
then set user.lifecycle.stage = "active_creator" confidence 0.9
```

| 元素 | 允许值 |
|---|---|
| 函数 | `count / sum / avg / max / min / last / exists / distinct_count` |
| 字段 | 已在 `tag_field_registry` 登记的事实与聚合字段，禁止自由 SQL |
| 时间窗 | `1d / 7d / 30d / 90d` |
| 逻辑 | `all / any / not`，最多嵌套 5 层 |
| 输出 | 枚举值或数值区间，必须匹配标签 `value_type` |

**安全与治理**：表达式解析为 AST 后在内存求值；解析失败、字段未登记、类型不匹配一律拒绝发布，不允许"运行时再发现"。每次发布生成不可变版本，运行中任务继续使用旧版本。

### 2.6 查询与人群圈选

| 能力 | 实现 | 说明 |
|---|---|---|
| 单客户画像 | `tag_assignments` 按主体查询 + Redis 缓存 | 返回标签值、来源、更新时间和置信度 |
| 标签命中人数 | Redis Bitmap `cardinality` | 秒级估算，不保证与明细完全一致 |
| 人群圈选 | Bitmap 交集/并集/差集 | 表达式仅支持标签与主体属性组合 |
| 精确成员列表 | 圈选后回查 PostgreSQL | 用于导出与触达，超过 10 万走异步任务 |
| 人群快照 | 计算后持久化 Bitmap 到对象存储 | 保证触达期间人群稳定，不受标签实时变化影响 |

**一致性规则**：圈选结果以快照为准，触达任务引用 `snapshot_id`；标签变更后不修改历史快照，只能重新圈选。避免"同一批用户收到两次不同规则的消息"。

### 2.9 多租户与权限

| 规则 | 说明 |
|---|---|
| 主体隔离 | `tenant` 标签只能由平台运营查看；企业管理员仅能看到本租户的 `tenant` 标签摘要 |
| 查询强制过滤 | 仓储层所有查询必须携带 `subject_type`，企业侧查询强制附加 `tenant_id` |
| 敏感标签 | 单独权限码 `tag:sensitive:read`，读取即写 `tag_access_audits`，导出需二次审批 |
| 平台超管 | 不能绕过审计；跨租户查看必须显式选择租户并记录原因 |
| 标签不授权 | 标签不参与 RBAC 判定，也不作为积分或权益发放依据 |

### 2.10 隐私与合规

1. 标签中禁止存储手机号、邮箱、身份证号、设备指纹原文；如需关联，使用不可逆哈希或内部 ID。
2. 敏感标签分类：消费能力、风控、未成年人、健康/宗教等特殊类别一律标记 `is_sensitive`，默认不参与营销定向。
3. 未成年人相关标签**仅用于保护性措施**（如限制付费、内容分级），不得用于营销、推荐加权或差别定价。
4. 导出必须审批、加水印、限制条数，并记录操作人、用途、时间与 IP。
5. 用户注销后，标签结果随主体进入删除流程；历史统计保留去标识化聚合值。
6. 标签口径需可向用户解释："为什么收到这条消息"应能对应到标签名称与规则摘要。

### 2.11 容量与性能（假设值，需压测校准）

| 项目 | 假设 | 说明 |
|---|---|---|
| 用户规模 | 100 万注册、50 万 MAU | `[ASSUMPTION]` |
| 标签数量 | 200 个，平均 5 个枚举值 | 位图总量约 1000 个 |
| 标签结果行数 | 100 万 × 30 ≈ 3000 万 | 单表需按月分区 |
| 位图内存 | 100 万 bit ≈ 125 KB/值，压缩后约 20–40 KB | 1000 个位图约 20–40 MB，Redis 可承载 |
| 圈选耗时 | 3 个标签交集 ≤ 200ms | 位图运算 |
| 全量计算 | 单标签 100 万主体 ≤ 10 分钟 | 16 分片并行 |

**容量信号**：全量任务连续 3 天超过 2 小时、Redis 位图内存超过实例 30%、`tag_assignments` 单月增长超过 2000 万行时，触发分区调整或拆分独立标签服务。

### 2.12 可观测性与故障处理

| 指标 | 阈值/规则 | 故障响应 |
|---|---|---|
| 标签任务失败率 | > 1% 持续 10 分钟告警 | 停止下游触达，检查数据源 |
| 标签任务超时 | 超过窗口 2 倍时长 | 降级为 T+1，保留旧标签值 |
| 标签命中率突变 | 环比波动 > 30% | 暂停发布新版本，人工核对口径 |
| 画像查询 P95 | > 300ms | 检查 Redis 命中率与慢查询 |
| 敏感标签访问 | 单账号 1 小时 > 500 次 | 触发安全告警并限流 |
| 位图与数据库不一致 | 抽样差异 > 0.5% | 从数据库全量重建位图 |
| 事件消费积压 | 延迟 > 10 分钟 | 扩容消费者，暂停低优先级标签 |

**降级策略**：Redis 不可用时，画像查询回源 PostgreSQL（限流保护）；计算任务失败时保留上一版本标签值并标记 `stale`，下游触达读取到 `stale` 时按策略跳过而非使用过期数据。

**重建路径**：Redis 位图可随时由 `tag_assignments` 全量重建，重建期间画像查询走数据库，圈选功能暂时关闭。

### 2.13 部署与灰度

1. 新增模块随 `SonicHub_api` 发布，通过配置开关 `tag.enabled` 控制路由注册。
2. 计算 Worker 与 API 同镜像、不同启动参数，独立副本数，避免批算拖垮在线查询。
3. 新标签先以 `shadow` 模式计算（只写历史不写当前值），观察 2 周后再切换生效。
4. 管理端功能按角色灰度：先开放标签查看，再开放圈选，最后开放导出。

| 属性 | 指标/规则 | 测量来源 | 频率 | 失败响应 | 本地检查路径 |

## 3. ADR

### ADR-TAG-001：标签作为现有 Go 单体内模块

| 字段 | 内容 |
|---|---|
| 状态 | Accepted |
| 背景 | 需要画像与圈选能力；现有系统已有用户、积分、生成、内容、消息模块；当前无独立扩容与团队边界证据 |
| 决策 | 在 `internal/tag` 实现独立模块，通过只读查询与事件接入现有数据，不新建独立服务 |
| 替代方案 | ① 新建独立标签平台服务：跨服务查询与一致性成本高，MVP 无收益；② 直接在各业务表加 `tags` 字段：口径无法治理、无法版本化、无法追溯，已拒绝 |
| 正向结果 | 复用事务、鉴权、审计与部署链路；开发与调试路径短 |
| 负向结果 | 与主服务共享故障域；批算可能影响在线查询，需要独立 Worker 与限流 |
| 可逆性 | 中；模块接口与事件已隔离，未来可平移为独立服务，需迁移计算任务与位图 |
| 重新评估条件 | 批算影响在线 SLO、标签资产需跨业务共享、或单日计算超过 4 小时 |
| 责任 | ASSUMED：数据/增长研发负责标签模块与计算任务；运营负责口径；合规负责敏感标签审批 |

### ADR-TAG-002：关系型事实 + 位图索引

| 字段 | 内容 |
|---|---|
| 状态 | Accepted |
| 背景 | 需要精确追溯标签来源，同时支持秒级人群估算 |
| 决策 | PostgreSQL 保存标签结果与历史，Redis Roaring Bitmap 保存命中索引，可随时重建 |
| 替代方案 | ① 只存位图：无法追溯单个客户画像与来源；② 只存关系表：圈选需要多表 JOIN，百万级不可接受；③ 引入列式数仓/标签平台：初期运维与成本过高 |
| 正向结果 | 查询快、可追溯、可重建；运维组件少 |
| 负向结果 | 存在双写不同步风险，需要每日对账与重建机制 |
| 可逆性 | 高；位图是可丢弃派生数据 |
| 重新评估条件 | 标签规模超过千万主体、或需要复杂多表行为分析 |

### ADR-TAG-003：受限 DSL，禁止动态脚本

| 字段 | 内容 |
|---|---|
| 状态 | Accepted |
| 背景 | 运营需要自定义口径，但标签直接影响触达与合规判断 |
| 决策 | 使用白名单函数与登记字段的表达式 DSL，解析为 AST 求值，发布前静态校验 |
| 替代方案 | ① 允许运营写 SQL：注入与性能风险不可控；② 允许 JavaScript/Lua 脚本：无法保证可解释与审计；③ 全部由研发硬编码：迭代慢，运营无法自助 |
| 正向结果 | 可解释、可校验、可版本化；敏感字段可强制审批 |
| 负向结果 | 表达能力受限，复杂口径仍需研发介入 |
| 可逆性 | 中；DSL 语法需向后兼容，历史版本必须可解析 |
| 重新评估条件 | 复杂口径占比超过 30%、或需要跨主体图关系计算 |

### ADR-TAG-004：标签与权限、积分解耦

| 字段 | 内容 |
|---|---|
| 状态 | Accepted |
| 背景 | 运营倾向用标签直接发放权益或限制功能，实现快但破坏单一事实源 |
| 决策 | 标签只输出画像与人群，权限由 `memberships`/RBAC 决定，积分由 `credit_accounts`/`credit_ledger` 决定 |
| 替代方案 | ① 用标签驱动权限：状态漂移会导致越权或误封；② 用标签缓存余额：与财务事实冲突 |
| 正向结果 | 责任边界清晰；标签可自由重算而不影响资金与权限 |
| 负向结果 | 权益发放需额外一层规则映射，运营不能"一键生效" |
| 可逆性 | 低；一旦标签参与权限判定，回退需大量数据修复 |
| 重新评估条件 | 不重新评估（架构不变量） |

## 4. 风险登记

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|

## 5. 分阶段落地

| 阶段 | 范围 | 交付物 | 退出条件 |
|---|---|---|---|
| M0 | 标签元数据、人工标签、客户 360 查询 | 表结构、Admin 标签列表、画像页 | 可创建标签并手工打标，审计可查 |
| M1 | 事实/统计标签、定时计算任务、位图索引 | 计算 Worker、10 个核心标签 | 覆盖率 ≥ 80%，T+1 06:00 前完成 |
| M2 | 规则 DSL、人群圈选、快照与触达对接 | 圈选台、消息中心对接 | 百万级圈选 ≤ 5 分钟，触达引用快照 |
| M3 | 敏感标签审批、导出审计、模型标签 | 审批流、导出水印、付费倾向/流失风险模型 | 敏感访问 100% 留痕，抽检准确率达标 |
| M4 | 性能与治理优化 | 分区、对账、自动重建、标签健康度看板 | 连续 2 周无 P1 告警 |

**实施顺序理由**：先建立元数据与治理，再上计算，最后开放圈选与导出。若先开放圈选，口径未治理会直接放大错误触达。
